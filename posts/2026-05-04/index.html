【セキュリティ】git push 1回でサーバーを乗っ取れる——GitHubに重大脆弱性、2時間で修正完了

■ 何が起きた？

先週、GitHubに重大な脆弱性（CVE-2026-3854、CVSS 8.7）が発見されました。

仕組みは「git pushコマンド実行時に、オプションの値が適切にチェックされずサーバーに渡される」というもの。攻撃者がリポジトリへのpushアクセス権を持っていれば、それだけで任意のコマンドをGitHubサーバー上で実行できる状態でした。

GitHubは報告を受けてから2時間以内に対応済みです（現在は安全）。GitHub Enterprise Serverについてはバージョン3.14.25以降でパッチ提供中です。

■ なぜ重要？

「コードを書いてpushする」という毎日の作業が脆弱性の引き金になりえた、ということです。フィッシング詐欺や怪しいファイルを開く必要はなく、普通の開発作業で発動する点が特徴的です。

なお今週はこれ以外にも、AIロボティクスフレームワーク「Hugging Face LeRobot」（★24,000）に**未パッチのRCE脆弱性（CVSS 9.3）**が公開されています。認証なしで外部からコマンドを実行できる状態が続いており、バージョン0.6.0での修正予定ですがまだリリースされていません。

■ 明日から使えるポイント

  • GitHub Enterprise Serverを自社運用している場合: 3.14.25以上へ更新（GitHub.comは対応済み）
  • Hugging Face LeRobotを使っている場合: バージョン0.6.0リリースまで、インターネット非公開環境での使用を推奨
  • 一般的な教訓: 重大な脆弱性が「普通の開発操作で発動する」ことがある。ツールのアップデート情報を週1回確認する習慣が有効です

【セキュリティ】Cursor と Gemini CLI に脆弱性——「AIに質問するだけ」で悪意あるコードが実行される

■ 何が起きた？

エンジニアが日常的に使うAIコーディングツールに、立て続けに脆弱性が報告されました。

Gemini CLI（Google のAIコーディングアシスタント） — CVSS 10.0（最高） CI/CD（自動テスト・デプロイの仕組み）環境で動かすと、リポジトリ内に仕込まれた悪意ある設定ファイルを自動で読み込み、ホストサーバー上で任意のコマンドを実行できる状態でした。Google は修正済み（バージョン 0.39.1 以上）。

Cursor（AI搭載コードエディタ） — CVE-2026-26268、CVSS 9.9（NVD評価）、バージョン 2.5 で修正済み リポジトリの .git フォルダ内に悪意ある「Git フック（コマンド実行の仕掛け）」を埋め込んでおき、開発者が Cursor の AI に「このコードを説明して」などの無害な質問をするだけで、AI が自動的に git コマンドを実行しフックが発動する、という手口です。米国公式脆弱性DB（NVD）は CVSS 9.9 と評価しましたが、Cursor 社は「8.0 が妥当」と独自評価を公表しています。バージョン 2.5 以降では修正済みです。

加えて「CursorJacking」と呼ばれる別の脆弱性（CVSS 8.2）も報告されており、インストール済みの拡張機能が Cursor 内部の SQLite データベースから API キーなどの認証情報にアクセスできる問題が現時点でも未修正のまま残っています。

■ なぜ重要？

「怪しいファイルを実行した」のではなく、AI に話しかけただけで攻撃が成立する点が従来と異なります。悪意あるコードが仕込まれたリポジトリを clone した時点で、その後の「普通の操作」が引き金になりえます。

■ 明日から使えるポイント

  • Gemini CLI を使っている方: 0.39.1 以上に更新（対応済み）
  • Cursor を使っている方: バージョン 2.5 以上に更新（git hook RCE は修正済み）。ただし拡張機能経由の API キー漏洩（CursorJacking）は引き続き未修正のため、信頼できない拡張機能を入れないよう注意
  • 一般的な教訓: AIツールが「信頼できる仕事の道具」になった分、それ自体が攻撃の入口になりうる。導入したツールは常に最新バージョンを保つことが重要です

【セキュリティ】攻撃者もAIを使う——北朝鮮ハッカーが Claude でマルウェアを自動生成

■ 何が起きた？

北朝鮮系ハッカーグループ（Famous Chollima）が、Anthropic の AI「Claude Opus」を使ってマルウェアを npm パッケージ（JavaScript のライブラリ配布サービス）に埋め込む攻撃キャンペーン「PromptMink」が確認されました。

手口は巧妙で、「第1層パッケージには怪しいコードなし → 第2層パッケージで初めて悪意あるコードが実行される」という二段階構造になっており、自動検出を回避しています。標的は主に暗号資産・Web3 系の開発者で、偽の採用求人メールでアクセスさせた上でマルウェアをインストールさせる手口も使われています。

■ なぜ重要？

「AI でコードを書く」のは開発者だけでなく、攻撃者も同じです。Claude Opus のような高性能 AI を使えば、マルウェアの生成・難読化・検出回避の品質が一気に上がります。セキュリティ研究者が「AI 支援攻撃の量産フェーズ」と呼ぶ状況が現実になってきました。

自分たちが日々使う AI ツールが、攻撃者の開発効率化にも利用されているという事実は、頭の片隅に置いておく価値があります。

■ 明日から使えるポイント

  • npm / pip でパッケージを追加するときは、スター数・最終更新日・作成者の素性を確認する習慣を
  • 採用メール経由で「試しにこのライブラリを使ってみて」という依頼には要注意
  • 組織として使える対策: Aikido / Socket などのサプライチェーン監視ツールの導入を検討する

■ 何が起きた？

今回のフィッシングには驚きがありました。送信元が noreply@appsheet.com——Googleの公式サービス「AppSheet」のアドレスだったのです。

メールの内容は「Facebookアカウントを削除する」という予告です。2025年3月から確認されている手口で、Googleの正規ドメインから届くためスパムフィルターをすり抜けます。今回は約3万件のアカウントが侵害されたと報告されています。

■ 明日から使えるポイント

  • 送信元ドメインが正規でも、リンク先のURLが本物かどうかを確認する
  • 「アカウント削除予告」「緊急の確認が必要」という文面は詐欺の典型。少しでも怪しいと思ったら上司に確認する
  • 2段階認証コードを入力させてくる画面は100%フィッシング。絶対に入力しない

【セキュリティ】今週の脆弱性は「バラバラな事故」ではない——AIツールと git を起点にした攻撃連鎖の構造

■ 今週の脆弱性を並べると見えてくるもの

今週は複数のセキュリティ事案を紹介しましたが、それぞれが独立した事故に見えて、実は一本の攻撃経路としてつながる構造を持っています。

① PyTorch Lightning の PyPI 汚染（サプライチェーン攻撃）
   → インストールした開発者の GitHub 認証情報・AWS キーが盗まれる

② 盗んだ認証情報でリポジトリに不正 push
   → .git/hooks（git 操作時に自動実行されるスクリプト）に罠を仕込む

③ 別の開発者がそのリポジトリを clone して Cursor で開く
   → Cursor の AI に「このコードを説明して」と話しかけるだけで
     AI が git コマンドを自動実行 → hooks が発動 → 実行環境を乗っ取られる
     （CVE-2026-26268、NVD: CVSS 9.9）

④ そのリポジトリの CI/CD が Gemini CLI を使っていれば
   → .gemini/ に仕込んだ設定でビルドサーバー上でも任意コマンドが実行される
     （CVSS 10.0）

⑤ LiteLLM（AI モデルへのリクエストを中継するゲートウェイ）が SQL インジェクションで侵害されれば
   → AI への問い合わせ・応答を改ざんできるため、
     Cursor や Gemini CLI を悪意ある操作に誘導することが理論上可能
     （CVE-2026-42208、CVSS 9.3、公開から 36 時間で悪用確認）

■ なぜ「AI ツール時代」に特有の問題なのか

従来の開発環境では「怪しいスクリプトを自分で実行する」という操作が最後のゲートになっていました。人間が実行ボタンを押す必要があったわけです。

AI コーディングツールはそのゲートを取り払いました。「コードを説明して」「リポジトリを整理して」という無害な指示でも、AI が判断して自律的に git コマンドを実行します。これは非常に便利ですが、同時に「git を自動で実行する」ということは、git の信頼モデルをそのまま引き継ぐことを意味します。リポジトリ内に仕込まれた罠も、まとめて実行してしまいます。

※ 補足: 今週の GitHub 脆弱性（CVE-2026-3854）については、GitHub の公式ブログで「研究者のテスト以外での実際の悪用は確認されていない」と発表されており、上記の連鎖は理論上のシナリオです。

■ 明日から使えるポイント

  • 開発者向け: 使っているツール（Cursor・Gemini CLI・LiteLLM）を最新バージョンに保つ。見知らぬリポジトリは clone 前にスターや履歴を確認する習慣を
  • チーム・組織向け: CI/CD で使うツールのバージョンを固定し（package-lock.json、pip freeze 等）、定期的に脆弱性スキャンをかける。Aikido・Socket などのサプライチェーン監視ツールの導入を検討する
  • 全員向け: 「AI が便利に自動化している部分」は、攻撃者から見ると「人間の確認をスキップできる部分」でもある

【セキュリティ】身代金の交渉を依頼した専門家が、攻撃者と組んでいた

■ 何が起きた？

アメリカでランサムウェア被害企業の「身代金交渉代理人」2名が、攻撃側のBlackCatグループからキックバックを受け取っていたとして懲役4年の有罪判決を受けました。

Ryan Goldberg（インシデント対応会社Sygnia所属）とKevin Martin（ランサムウェア交渉専門会社DigitalMint所属）は、被害企業の依頼で「味方として」交渉を行いながら、支払われた身代金の20%を攻撃者に渡す契約を結んでいました。製薬・医療機器・エンジニアリング等5社以上が標的になっており、タンパの医療機器メーカーへの127万ドルの支払いのうち約25万ドルが攻撃者側に流れた計算です。

■ なぜ重要？

セキュリティ事故が起きたとき、「専門家に任せる」は正しい判断です。しかしその専門家の利益が、依頼者と一致しているかどうかは別の問題です。インシデント対応業者は構造上「攻撃者の知識と接点を持つ人間」です。その立場を利用した内通が現実に起きました。

これはセキュリティ業界に限った話ではありません。「自分たちにはわからない専門領域を外部に委ねる」構造はどの業務にも存在します。委任すること自体は問題ではなく、「委任先が本当に自分たちの側を向いているか」を確認する仕組みを持つことが重要です。

■ 明日から使えるポイント

  • 外部委託先（セキュリティに限らず）の進捗・費用・判断根拠を、社内の誰かが直接確認できる体制を作る
  • 選定時は過去の実績・第三者評価・顧客参照を確認する（信用の事前担保）
  • 単一業者への全面委任は避け、重要な判断は社内で一度噛み砕いてから承認する

【セキュリティ】セキュリティ会社が侵害される——守る側が崩れるとき

■ 何が起きた？

今週、セキュリティ企業2社が相次いで侵害されました。

Trellix（ウイルス対策・EDRで知られるセキュリティ企業）: ソースコードリポジトリへの不正アクセスが確認されました。製品コードが流出した可能性があり、リバースエンジニアリングや新たな脆弱性の発見につながるリスクがあります。

■ なぜ重要？

いえらぶも、顧客から見れば「信頼して使っているサービス」です。Trellixと同じ立場——つまり、侵害される側になりうる。

注目したいのは、Trellixがこの事件にどう対応したかです。侵害を確認した後、フォレンジック専門会社に依頼し、当局に通報し、公式に情報開示しています。「バレたくない」ではなく「早く・正直に・対処する」を選んだ。それがサービス提供者としての信頼回復の第一歩です。

何かが起きたときに慌てず動けるかどうかは、事前に決めておくかどうかで大きく変わります。

■ 明日から使えるポイント

  • 顧客への開示タイミングと文面は、後手に回るほど信頼が傷つく。「完全に解明してから」ではなく「わかっていることを早く」が鉄則
  • 定期的なセキュリティ棚卸しは、問題を防ぐためだけでなく「何かあっても対応できる」という自信を組織に持たせるためにも有効

「Googleから届いたメールだから安全」は、もう判断基準になりません。AppSheetのような正規サービスは「誰でもメールを送れる仕組み」を持っており、攻撃者がその仕組みを借りることで、フィルターの目をかいくぐれます。送信元ドメインの信頼性と、メールの内容の信頼性は、別々に判断する必要があります。
